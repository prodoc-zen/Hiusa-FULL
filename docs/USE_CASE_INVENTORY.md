### Legend

**Scope tag** (why a use case is in this inventory):
- `PAPER`: named in the capstone paper. Cite the figure, module code, or table (for example `PAPER(Fig.29, M5.1)` or `PAPER(Table 24)`).
- `DOCS`: named in the team's own use-case docs or system-flow doc but not explicitly in the paper. Cite the UC id or file (for example `DOCS(UC-07)`).
- `EXTENDED`: genuinely beyond the paper's stated scope, with a one-line justification tied either to the dean's feedback or to a real, valuable gap found in recon.
- `INFERRED`: implied by the paper or docs but not stated outright (for example a supporting screen the stated feature cannot function without).

**Current status on main** (what recon actually found, not what any doc claims):
- `BUILT`: implemented and wired end to end on `main`, per client-map.md / server-map.md.
- `PARTIAL`: exists but with a named gap (missing client, missing edge case, narrowed access, etc.).
- `BROKEN`: present but throws, 500s, or cannot complete as written.
- `MISSING`: no implementation on `main` at all (may exist on `wip/sao-extensions` or nowhere).

**Proof type**:
- `TEST`: an automated check. Names the test to write, or the existing test file if one already covers it.
- `BROWSER`: a Playwright walkthrough step with a screenshot at a named viewport.
- `BOTH`: both are needed for meaningful confidence (typical for anything money-, vote-, or stock-affecting).

Live browser verification is largely **pending live verification** across this whole document: the walkthrough recon pass could not get past `/select-organization` because the dev MariaDB instance on port 3307 was down for that whole session (`walkthrough.md`), so almost every BROWSER proof step below is unexecuted, not failing. Where a fuller walkthrough exists elsewhere, it supersedes this note.

## 7. UI Soul Acceptance Criteria

Applies to every screen in section 3's catalog. Each criterion below cites the specific design-audit.md evidence it exists to fix, because the dean's "no soul" complaint needs to be answered with checkable criteria, not vibes.

1. **Role-aware greeting and a "what needs your attention now" block on every dashboard.** Fixes: only 1 of 5 dashboards (`AdminHomePage`) currently personalizes at all; the other four use static role-generic titles like "Officer Dashboard" and "University Oversight" (design-audit.md §5 finding 4).
2. **One clear primary metric per dashboard section, with context (trend, comparison).** Fixes: most stat strips are plain `<dd>` text with no trend indicator (design-audit.md §5 finding 5).
3. **Designed empty states with a helpful next action, not bare text.** Fixes: the common pattern is a bare `<p>No X yet.</p>` (design-audit.md §5 finding 6); `StudentHomePage`'s "Your feed is quiet" and the branch's `ManageVenuesPage` `Building` icon are the two positive examples to generalize from.
4. **Animated skeletons, never plain text or a spinner, while loading.** Fixes: client-map.md's per-page table shows a real mix of `skel`/`spin`/`none` across the app; every non-`skel` row is a target.
5. **Human microcopy instead of system-speak.** Fixes: design-audit.md §5 finding 10 names the exact offending phrases ("Publishing overview," "Administration workspace," "Operations snapshot," "University Oversight") and contrasts them with the one genuinely human line found in the whole audit (`DashboardPage.jsx:143`, "Start with deadlines, then check events, funds, and merchandise queues").
6. **Charts where numbers tell a story.** Fixes: design-audit.md §5 finding 5, only 2 of 5 dashboards (Admin, Finance) have any chart at all, despite `DataDonutChart` and `FinancialForecastChart` already existing as shared components ready to reuse on Officer (task-status-by-percentage), Department Head (approvals-by-type), and Elections (partylist vote share, currently absent per §4).
7. **Status colors on-brand (`#16A34A`, `#F59E0B`, `#DC2626`), not stock Tailwind.** Fixes: design-audit.md §2's single largest finding, `bg-red-50/text-red-700`, `bg-amber-50/text-amber-700`, `bg-emerald-50/text-emerald-700` appear 224/51/53+ times respectively, the exact default look of any Tailwind admin scaffold, and the opposite of CLAUDE.md's own "use exact hex values" rule.
8. **A single reusable page header component instead of the band hand-copied across 20 files.** Fixes: design-audit.md §5 finding 1 identifies the same `bg-[#0F2F62]` header recipe retyped by hand in 20 files with zero shared component, which is exactly why it never varies in emphasis or tone.
9. **Purposeful motion that respects reduced motion.** Fixes: design-audit.md §5 finding 9, zero animation library use anywhere, only CSS hover transitions; cross-reference S-16.
10. **Consistent card and list patterns.** Fixes: design-audit.md §5 finding 2, no `components/ui/Card.jsx` exists despite design.md naming it as a recommended primitive; the literal string `rounded-lg border border-[#DDE7EF] bg-white` is hand-typed 29 times in `MerchandisePage.jsx` alone, 31 in `EventsPage.jsx`, 18 in `FinancePage.jsx`.
11. **Brand palette, Poppins only, lucide icons only.** Fixes: mostly already true (design-audit.md §2 confirms genuinely good palette discipline, no random blue shades found); the two real violations are the Arial `font-family` hits inside PDF/print export helpers (`FinancePage.jsx:174`, `SuperAdminFinancialReportsPage.jsx:27`), which make exported reports look like a different, unbranded product from the app around them.

## 9. Decisions

All items below were open questions in an earlier pass of this inventory. Under the owner's delegation the orchestrator has decided each one; the rationale and any residual implementation gap are recorded here so the same ground is not re-litigated at the defense.

(a) **Finance access for SBO Officer and Department Head, decided.** Finance READ access (transaction history, OLS forecast and safe-spending view, financial reports and status, event budget monitoring) is restored for SBO_OFFICER and DEPARTMENT_HEAD, per the paper's own Fig.35/36 and Table 24 (M6.2, M6.8, M6.9). Writes (create/edit transactions, budgets, forecasts) stay ADMIN-only. Financial reports keep their Department Head then SAO chain; budgets follow decision (i). Rationale: commit `9057f97`'s narrowing to ADMIN-only reads has no support in the paper's actor list, which explicitly grants both roles read access. Status: implemented 2026-10-02. The ledger, budget allocation, financial insights and transaction history pages open read-only for both roles, with a view-only note and no write controls; the server already restricted every write to ADMIN.

(b) **Voting electorate, decided.** ADMIN, SBO_OFFICER and STUDENT vote, once per position. DEPARTMENT_HEAD oversees elections (approves them and reads results) and does not vote, because it belongs to a college, not to an organization; this narrows the original decision, which had all four operating roles voting, per Table 24's "Cast a Secure Vote" asterisks and commit `9057f97` ("restored voting for admin, sbo officer, department head, and student"). Fig.27's Student-only narrative is the illustrative use-case walkthrough, not the operative access rule (the note on Fig.27 stays). Shipped, with the Department Head change on 2026-10-09 (ELEC-06, ELEC-08, scope.md watch-list item 3, server-map.md §8).

(c) **Role naming, decided.** Chapter III's framing (Admin, SBO Officer, Department Head, Student) is operative for this inventory and the codebase, not Chapter I's Definition-of-Terms framing (Admin, Adviser, Officer, Student). DEPARTMENT_HEAD is labelled in the UI and docs as the adviser/oversight role, and since 2026-10-09 as the college oversight role: it oversees every student organization in one college rather than one organization. "Adviser" survives only as a `position_title` under ADMIN, not a distinct RBAC role, and is a different thing from DEPARTMENT_HEAD. Rationale: Chapter III is the methodology/use-case/functional-spec chapter and is used consistently through the program specification; the code's five-role enum (`SUPER_ADMIN`, `ADMIN`, `SBO_OFFICER`, `DEPARTMENT_HEAD`, `STUDENT`) already reflects this choice. (The adviser questionnaire EVAL-03 that this once settled was retired with the Evaluation module.)

(d) **Evaluation module, decided live and then retired.** EVAL-01 through EVAL-06 (section 6) were decided as a live data-collection instrument, gated behind an informed-consent step, that counted toward the paper's required up-to-450-respondent acceptability study, with every aggregate anonymized and any group under 3 respondents shown as a bare count. The module was built and then removed for all roles on 2026-10-06 (commit 46790dd). The decision no longer counts toward in-app respondent counts: SO1 and SO4 are assessed through the study's own research process (the paper's questionnaire) outside the application, and the Study Objectives page says so. Existing survey records are retained without user-facing access. The consent and anonymization rules belong to the paper's data gathering procedure and ethics paragraph, outside the system (scope.md §7, lines 1127-1128).

(e) **Paper scope addendum, decided.** A scope addendum will document the extended SAO modules (organizations, admins, official announcements, the Financial Approval Center, and the SAOX-01 through SAOX-13 governance items in section 6) as a delegated, defense-facing scope extension, rather than leaving SAO as either undisclosed scope creep or silently folded into the paper's four-actor narrative. Rationale: dean feedback names SAO self-serve governance a priority; the paper as submitted has zero SAO mention, and neither the canonical use-case diagram nor the docx business-use-case references include a fifth actor (scope.md §3, §9 watch-list item 2; use-cases-docs.md §4), so this needs reconciling before the defense, not discovered during it.

(f) **Audit log access, decided as shipped.** SUPER_ADMIN sees all organizations, ADMIN sees its own organization only, per the shipped route (`GET /audit-logs`, `role:SUPER_ADMIN,ADMIN`). `HIUSA_Administrator_Cheat_Sheet.md`'s framing of this as an "SAO-exclusive feature" is the artifact to correct, not the code (AUD-01, SAO-05).

(g) **Budget approval, superseded by (i).** The original two-stage plan: Budget approval becomes DEPARTMENT_HEAD endorsement then SUPER_ADMIN final approval, mirroring the financial report chain, rather than picking one of the two conflicting sources outright (paper Chapter III M6.6/Fig.43 names Department Head as approver; `HIUSA_System_Flow.md` names SAO). Status: PARTIAL as of this inventory. See FIN-05 for the exact code gap: today's single-stage `ApprovalRequest` with `required_role` = `config('approvals.routes.budget')` = `SUPER_ADMIN`, `canReview()`'s strict role equality, and `BudgetController::reopenApproval`'s hardcoded `'SUPER_ADMIN'` reopen target all need to become a two-hop chain that reopens to DEPARTMENT_HEAD, not SUPER_ADMIN.

(h) **Task-delegation scoring criteria, decided: one formula that honours all three framings.** The paper names the Rule-Based Weighted Scoring criteria three ways (Chapter I scope: "role, workload, availability"; Chapter III AI System Architecture: "workload, role relevance, assignment recency"; Table 24 M7.2: "Role, Workload, and Past Performance"). The shipped code scores Role/Workload/Performance at 40/35/25 with availability as an eligibility gate, and does not score recency. Decision: keep availability as the eligibility gate (Chapter I) and score four factors: role relevance 0.35, workload 0.30, past performance (on-time completion rate) 0.20, and assignment recency 0.15 (an officer assigned very recently scores lower, spreading work). The server `TaskDelegationService` and the ai-service `task_delegation` engine must stay in parity, and the "Why?" disclosure shows every factor, its weight and the officer's raw inputs. Rationale: every criterion any chapter names is present and explained, so the panel can trace the formula to whichever page they read. Status: implemented 2026-10-02. Recency is min(1, days since the officer's last assignment / a 14-day window) x 100, and an officer never assigned scores 100; `tasks.assigned_at` is stamped by the Task model on every assignment, including reassignment. `TaskDelegationService`, the TaskController PHP fallback and the ai-service engine share the formula, and `AiFallbackParityTest` checks the PHP fallback against the live Python engine on the same officer.

(i) **Budget approval, decided single-stage by Department Head (supersedes g).** The collaborator's later routing work and the paper's own Chapter III (M6.6, Fig. 43) both put budget approval with the Department Head, and the SAO has no ledger access by the collaborator's rule. Shipped: `config/approvals.php` routes `budget` to DEPARTMENT_HEAD with `budget_final` set to null. Setting `budget_final` to 'SUPER_ADMIN' re-enables an SAO second stage on top; setting `routes.budget` to 'ADMIN' restores in-organization approval. A budget counts as available money on every dashboard only once its submission status is approved. Status: implemented.
